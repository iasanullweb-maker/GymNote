# GymNote 변경별 검증

1. 현재 디렉터리에서 GymNote 저장소 루트와 적용 지침을 확인한다. 검사 대상 커밋·비교 기준·미커밋 변경을 기록한다. 작업 시작 커밋이 있으면 그것과 비교한다. `main...HEAD`만으로는 아직 커밋하지 않은 수정이 누락되므로 staged·unstaged·본인 새 파일도 확인한다. 다른 대화의 변경을 검사 대상과 혼동하지 않는다.
2. [검사 선택표](references/checks.md)에서 동작 영향에 맞는 최소 검사 묶음을 선택한다. 파일 경로는 단서이며 호출자·공유 모델·저장/권한 영향까지 검토한다. 명령은 현재 저장소의 CI와 README를 확인해 사용한다.
3. 필요한 실행기 버전과 환경을 확인한다. PATH에 도구가 없는 것과 실행 가능한 번들 런타임이 없는 것을 구분한다. Codex의 런타임 조회 도구가 있으면 활용한다. Swift/Xcode 없는 환경에서 문법 확인·웹 검사로 전체 iOS 빌드 성공을 선언하지 않는다. 운영 DB·운영 작업 큐를 테스트에 사용하지 않는다.
4. 검사를 실행하고 종료 코드와 실패/건너뜀 내역을 확인한다. 실패하면 재현·원인 분석을 수행한다. 수정까지 요청되었거나 기존 구현 요청에 필요한 수정이면 해당 범위에서 고치고 관련 검사만 다시 실행한다. 검사만 요청받았으면 제품·테스트를 수정하지 않고 실패 근거와 수정 제안을 보고한다. 실행 불가, 기존 실패, 본인 변경의 실패를 구분한다. 테스트를 약화하거나 삭제해 통과시키지 않는다.
5. 결과마다 대상 커밋(미커밋이면 그 사실), 환경, 명령, 통과/실패/건너뜀/미실행과 이유를 기록한다. CI 결과를 재사용하면 job 대상 SHA가 검증 대상과 일치하는지 확인한다. 이전 성공은 새 변경의 검증 결과가 아니다.

작은 UI·문서 수정은 검토·공백 검사와 가벼운 검사를 적용한다. 로그인·보안·저장 변경은 필요한 검사를 즉시 실행하고, 전체 iOS 검사·빌드는 변경을 모아 통합 검증 또는 배포 직전에 실행한다. 전체 빌드 미실행 여부는 항상 보고한다. 원격 검사 실행은 기존 승인 범위에 따르며 배포 승인으로 확대하지 않는다.

검증 요청만 받은 경우 제품 변경·커밋·통합을 임의로 추가하지 않는다. 구현 작업의 일부라면 결과를 담당 보고서와 작업 완료 절차에 전달한다.
