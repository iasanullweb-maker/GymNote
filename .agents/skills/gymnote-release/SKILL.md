# GymNote 배포

현재 디렉터리에서 GymNote 루트·적용 지침을 확인한다. `HANDOFF.md` 최신 상태와 `.github/workflows/check.yml`, `build.yml`을 읽고 [배포 확인 절차](references/release.md)를 해당 단계에서 따른다. 과거 버전·승인을 이번 배포의 근거로 삼지 않는다.

## 준비

- 배포할 앱 변경·커밋과 포함/제외 범위를 확정한다. 원본·워크트리의 브랜치와 미커밋 변경, 원격과의 차이를 확인하고 다른 작업을 보존한다. 로컬 main의 모든 변경이 이번 승인 대상이라고 가정하지 않는다.
- gymnote-verify가 있으면 변경별 검사와 배포 전 전체 iOS 검증을 수행한다. 없으면 현재 CI와 검사 도구를 확인한다. 필요한 iOS·계정·DB 검사 및 앱/위젯 Release 빌드가 미검증·실패 상태이면 배포 실행으로 넘어가지 않는다. 불가능한 항목과 필요한 환경을 보고한다.
- 실제 배포 SHA와 검증 SHA를 비교한다. 동일 SHA를 우선 사용하며 병합/문서 변경으로 다르면 앱·위젯·공유 코드·리소스·테스트·설정·의존성·서버·빌드 도구/CI의 트리 일치를 확인하고 근거를 기록한다. 파일명 목록만 같다는 이유로 검증을 재사용하지 않는다. 차이가 있으면 관련 검사를 다시 실행한다.
- 서버 변경은 gymnote-data-change 또는 해당 설정 문서에서 운영 적용·구버전 호환성·배포 순서를 확인한다. 앱 빌드 성공을 서버 적용 완료로 보고하지 않는다.

## 권한과 대상 고정

배포 준비 요청이면 검증 결과, 포함 변경·대상 SHA·미확인 항목을 제시한다. 실제 배포는 사용자 승인 범위로 진행하며 이미 같은 범위를 승인했다면 재승인을 요구하지 않는다. 스킬 호출만으로 운영 SQL·유료 서비스·외부 메시지까지 승인됐다고 해석하지 않는다.

main push는 현재 설정에서 공개 배포를 시작한다. push 직전에 대상 SHA와 승인 범위가 유지되는지 다시 확인한다. 다른 작업이 main에 추가되었으면 승인받은 커밋 범위를 보존하고 해당 변경을 포함할 권한이 불명확한 부분만 조율한다. 강제 push·reset·임의 stash를 사용하지 않는다. 기존 통합 잠금 아래 로컬 병합·원격 대상 준비를 직렬화하며 긴 CI 대기 중에는 잠금을 해제한다.

## 실행과 확인

승인된 브랜치/커밋만 push하거나 현재 워크플로에 지원되는 수동 실행을 사용한다. 실제 run ID·head SHA·브랜치를 기록하고 해당 run의 진행·실패 로그를 확인한다. 대상이 변한 배포를 조용히 재시도하지 않는다.

실패 뒤에는 실행 중 run, 이미 공개된 릴리스, AltStore 갱신 상태를 먼저 조회한다. 부분 성공을 확인하지 않고 재실행하면 버전·latest·소스가 엇갈릴 수 있다. 완료는 대상 run 성공과 IPA·릴리스·AltStore의 버전/빌드·URL·크기·대상 SHA를 대조한 뒤 보고한다. 기기 설치와 실제 사용 확인은 별도 결과로 남긴다.

gymnote-handoff 또는 본인 보고 절차로 대상 커밋, 검증 결과, run/릴리스 링크, 버전·빌드·IPA SHA-256, 서버 상태, 미실행 실기기 항목을 기록한다. 배포 확인만 요청받았으면 새 배포를 시작하지 않는다.
