# GymNote 서버·데이터 변경

현재 디렉터리에서 GymNote 루트·지침과 요청 범위를 확인한다. 앱 코드·격리 DB 검사·운영 적용 중 요청 단계를 구분한다. 스킬 호출이나 앱 배포 승인만으로 운영 DB 변경을 승인받았다고 해석하지 않는다. 해당 변경이 이미 승인됐으면 재승인을 요구하지 않는다.

## 데이터 경계와 상태

- `docs/LOGIN_SETUP.md`, `docs/RECORD_CATALOG_SETUP.md`, `docs/SOCIAL_SETUP.md` 중 관련 문서를 읽는다. HANDOFF 최신 관련 항목, supabase/migrations/와 관련 함수를 확인한다. 과거 적용 기록, 현재 읽기 전용 확인, 미확인을 구분한다.
- 계정별 개인 기록·게스트 원본/가져오기 백업·공개 친구 기록·공통 종목을 구분한다. 변경 전후 소유자, 저장 위치, 서버/기기 사본, 충돌 규칙, 구버전 동작과 실패 시 보존할 데이터를 정리한다.
- 관리자는 서버 권한 조회가 근거다. 이메일·user_metadata·클라이언트 플래그를 인증 근거로 바꾸지 않는다. 앱/위젯/로그/Git에 service_role·secret·SMTP 비밀번호·세션 토큰을 넣지 않는다. 위젯과 인증 토큰을 공유하지 않는다.

## 구현과 격리 검증

- 기존 마이그레이션 적용 이력을 임의로 다시 쓰지 않는다. 필요한 변경은 새 마이그레이션으로 작성하고 적용 순서·전제·호환성을 명시한다. 테이블 재생성·기록 삭제·권한 완화로 문제를 우회하지 않는다.
- 저장·동기화는 계정 전환, 게스트 가져오기, 오프라인/복구, 버전 충돌, 쓰기 실패·지연 응답에서 개인 원본 보존을 확인한다. RPC는 소유자 허용과 다른 계정/anon/폐기 세션 차단을 함께 확인한다.
- gymnote-verify 또는 현재 `.github/workflows/check.yml`의 격리 PostgreSQL·계정 검사 절차를 따른다. `scripts/auth_test_schema.sql`, test_*.sql은 운영에 실행하지 않는다. 본인 담당 범위에서 회귀를 실행하고 불가능한 검사는 명시한다.
- 앱 새/구버전과 서버 변경 전/후 조합을 검토한다. 업데이트 필요 안내·서버 선적용 등 변경에 필요한 배포 순서를 기록한다. 새 기능뿐 아니라 기존 로그인·기록 조회도 확인한다.

## 승인된 운영 적용

1. 대상 프로젝트·승인된 SQL/함수·커밋·현재 적용 상태를 읽기 전용으로 확인한다. 이미 적용된 migration을 새 프로젝트 안내만 보고 반복 실행하지 않는다.
2. 실제 위험에 맞춰 데이터 보존/복구 수단과 전제를 확인한다. FK·고아 행·중복·타입 변경 문제가 있으면 결과를 먼저 제시하고 기존 자료를 임의로 삭제하지 않는다. 사용자 판단이 필요한 처리만 조율한다.
3. 준비한 정확한 변경만 해당 프로젝트에 적용한다. 함수·OAuth·환경 설정은 SQL과 별도 확인한다. 실패 뒤에는 트랜잭션·부분 적용 상태를 확인하고 맹목적으로 재실행하지 않는다.
4. 적용 후 스키마/RPC/FK·권한과 테스트 계정 흐름을 확인한다. 운영에 테스트 스키마·대량 합성 데이터를 넣지 않는다. 확인에 기록 변경이 필요하면 지정 테스트 계정/승인 범위를 따른다.

코드 구현, 격리 검사, 운영 migration/함수/설정 적용, 실제 앱 두 계정 결과를 따로 기록한다. 완료는 본인 파일 검토·커밋·로컬 통합과 gymnote-handoff 또는 배정 보고 절차를 따르며 미적용 서버 작업을 남긴다.
