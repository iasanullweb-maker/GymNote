# GymNote 오류 재현과 수정

현재 디렉터리에서 GymNote 루트·적용 지침과 요청 범위를 확인한다. 조사만 요청받았으면 진단·재현 근거를 제공하고 제품·운영 설정을 임의로 바꾸지 않는다. 수정 요청이면 gymnote-task의 범위·완료 절차도 적용한다.

## 증거와 재현

1. 기대 동작과 실제 결과, 마지막 정상 상태, 발생 순서·빈도, 기기/OS·앱 버전/빌드, 설치 경로와 관련 커밋을 모은다. CI는 run ID·head SHA·실패 job/step, 서버는 적용 상태·응답 종류를 확인한다. 필요한 정보만 질문하고 독립 조사는 계속한다.
2. HANDOFF 최신 관련 항목, 기능 README/설정 문서, 기존 테스트를 읽는다. 최신이라는 제목만 믿지 않고 시각·버전·SHA와 연결한다. 배포 바이너리와 로컬 HEAD가 다르면 조사 대상을 명시한다.
3. 원본 로그·화면은 보존하고 작업 사본은 Git 제외 `.validation-tools/` 또는 `simulation/runs/`에 둔다. 합성 데이터·격리 저장소·테스트 계정을 사용한다. 개인 기록·토큰·이메일·친구 코드를 보고서/Git에 복사하지 않는다.
4. 관찰 사실, 가설, 반증 방법을 구분한다. 앱 로직·서버 미적용/권한·네트워크·설치/재서명·기기 환경 중 증거가 가리키는 경로부터 검사한다. 화면만으로 실행·저장 성공을 단정하지 않는다.

## 조사 경로

- 저장·계정 전환: Shared/와 App/의 호출 경로, 계정별 저장·버전 충돌·지연 응답, 관련 테스트를 확인한다. 원본 삭제·자동 병합·권한 완화로 실패를 숨기지 않는다.
- UI·편집 흐름: 관련 XCTest와 gymnote-ux-check를 사용한다. 웹에서만 재현되면 제품 Swift 문제로 단정하지 않는다.
- RPC·권한: `docs/LOGIN_SETUP.md`, `docs/SOCIAL_SETUP.md`, `docs/RECORD_CATALOG_SETUP.md` 중 관련 문서와 gymnote-data-change를 사용한다. 코드 존재와 운영 배포를 구분한다.
- CI: 현재 check.yml/build.yml과 정확한 실패 로그의 최초 원인 오류를 확인한다. 다른 SHA의 성공이나 취소된 run을 근거로 삼지 않는다.
- 설치·클라우드 첫 실행: `simulation/cloud/README.md`와 최신 조사 기록을 확인한다. 구조 검사·재서명·설치·프로세스 실행·첫 화면을 구분한다. 바이너리/개인 원본 로그는 커밋하지 않는다.

## 수정과 재검증

실패 조건을 재현할 수 있고 회귀 가치가 있을 때만 검사를 추가한다. 범위를 좁힌 수정 후 원래 재현 과제와 관련 gymnote-verify 검사를 다시 실행한다. 새 근거 없이 같은 재시도를 반복하지 않고 다음 관측·환경/사용자 판단이 필요한 지점을 설명한다.

결과에는 근거 있는 원인 또는 미확정 범위, 재현 조건, 수정 내용, 검사/미실행을 남긴다. 조사 환경에서 해결한 것과 운영/실기기 확인을 구분한다. 승인된 수정은 검토·커밋·로컬 통합하고 gymnote-handoff 또는 배정 보고서에 익명화한 근거를 기록한다.
