# USB 정지 화면 오인 수정·실기기 확인 — 2026-10-10

사용자가 USB iPad 연결 후 작업을 요청했다. [이전 복구 구현](usb-recovery-implementation.md)에 실제 기기 검증을 추가했다. 작업 경로는 원본 저장소의 `.worktrees/ux-coordinator`, 브랜치는 `codex/ux-coordinator`다. 제품 Swift 코드는 변경하지 않았다.

## 관찰과 판단

- Chrome 탭이 모두 닫힌 상태에서 로컬 HTTP 스트림을 읽고 즉시 버리는 비교를 수행했다. 기존 watchdog에서는 약 7초 전송 뒤 무전송 구간을 장애로 처리하고 세션을 반복 재시작했다. RCTL 활성화만으로는 이 패턴이 해결되지 않았다.
- 진단용 90초 재시작 보류 및 구독자 없는 관찰에서 긴 무전송 후 같은 세션의 프레임이 다시 도착했다. 약 60초 간격의 전송 재개도 관찰했지만, 시계 갱신이나 사용자의 직접 조작 중 어느 것이 원인인지는 확인하지 않았다.
- 읽기 전용 DisplayService 상태 질의가 정상 응답했다. RR 전송 작업이 살아 있고 로컬 전송 오류·UDP 체크섬 오류가 없었다. 피드백 목적지와 실제 RTP 발신지가 일치했다. 이는 로컬 경로 증거이며 기기가 피드백을 수신했다는 증명은 아니다.
- 따라서 무전송 시간을 무조건 연결 단절로 간주한 USB 뷰어 복구 정책이 이번 반복 재시작의 유력 원인이다. 기존 모든 장애의 원인이 동일하다는 결론이나 GymNote 제품 전체의 무결성 판정은 하지 않는다.

## 변경

조용한 화면에서는 별도 DisplayService 연결로 상태를 질의한다. 10초 이상 간격, 질의 제한 4초, 연결 종료 제한 2초이며 응답 내용은 보관하지 않는다. 최근 15초 안에 정상 응답이 있고, 현재 서비스가 살아 있으며, 마지막 전송 이후 미반영 PC 입력이 없으면 `video_idle`로 표시하고 무전송 watchdog 재시작을 보류한다. 정상 응답이 낡거나 오류가 발생하면 기존 복구를 유지한다. 터널 단절 분류·worker 교체 상한도 유지한다.

브라우저는 5초 이내에 받은 `video_idle` 상태만 사용한다. 데이터가 들어오는데 디코더가 멈춘 경우나 건강 상태 응답이 끊긴 경우에는 기존 PLI/재시작이 동작한다. HID 입력은 내용을 읽거나 저장하지 않고 큐 수락 시각만 기록해 미반영 입력 뒤에는 idle 판정을 하지 않는다.

진단에 로컬 RR/RCTL/receipt 전송 횟수, 송수신 주소 일치 여부(boolean), UDP 체크섬 오류 횟수를 추가했다. 주소·포트·기기 식별자는 출력하지 않는다. `/gymnote/observe-idle` POST는 진단용으로만 90초 보류하며 기본값은 0이다. `/gymnote/stop` POST는 기존 정리 경로로 본인 서버를 종료한다. 기존 loopback 제한·요청 검증·오디오/클립보드 차단을 유지한다.

## 검증

- Python 3.12.10 / pymobiledevice3 11.26.0: recovery 검사 18개 통과. 상태 질의 실패·단절 분류, 미반영 입력, 오래된 정상 응답, 개인정보 미보관, 재시도 상한과 checksum 경계를 검사했다.
- adapter: 기존 개인정보 경로 8개 차단, 오디오 차단, 안전한 health 응답, 90초 진단 보류, 정상 종료, 변경된 upstream 거부 통과.
- Node 24.21.0: 실제 패치된 JS 문법 및 lifecycle·coordinates·reconnect·idle 검사 통과. idle 검사에서는 정상 정지 화면의 불필요한 재시작 차단과 오래된 health/디코더 정지의 복구 유지를 확인했다.
- Chrome 없는 180초 목표 스트림 관찰(종료 포함 183.5초): 1,543개 HTTP 프레임 메시지, 2,434,873 bytes, 읽기 오류 없음. 초기 시작 구간 이후 generation 2 유지, 무전송 후 같은 연결에서 재개. 관찰 구간에서 gap/reorder/corrupt 및 피드백 오류 0. 영상 바이트는 즉시 버리고 카운터만 Git 제외 진단 경로에 저장했다.
- 사용자가 Chrome 한 탭에서 뷰어와 GymNote 화면을 열었다. PC 다른 앱으로 10초 이동 후 복귀하고 뷰어의 계획/설정 탭 조작을 요청했으며, 사용자가 **“양쪽 모두 바뀌어”**라고 확인했다. 같은 generation 3에서 AU/HTTP 카운터 증가도 관찰했다. 초기 구독 시작에 따른 generation 변경을 중간 단절로 해석하지 않는다.

화면 이미지·음성·클립보드·HID 본문은 저장하지 않았다. 강제 USB 분리, 데이터 변경, 전체 iOS 빌드·XCTest, 원격 push·배포는 수행하지 않았다. 변경은 파일 검토·`git diff --check` 후 커밋하고 공통 잠금 스크립트로 로컬 main에 통합한다. 최종 커밋·통합 여부는 완료 응답에 기록한다.

## 남은 한계

정상 제어 응답은 영상 인코더의 정상 동작까지 증명하지 않는다. PC 입력 없이 인코더만 멈춘 장애는 정지 화면과 구분하지 못할 수 있다. 이번 결과는 정지 화면과 한 번의 PC 앱 전환/조작 확인이며, 10분 반복 시험·장기 안정성·실제 터널 단절 후 자동 복구는 추가 실기기 검증 대상이다. 기존 closed-userspace 단절은 별도 실제 오류이므로 이번 idle 판정으로 없어진 것으로 보고하지 않는다.

## 추가 확인: Chrome 10분 관찰

사용자의 추가 확인 요청에 따라 코드 `9da3205`(로컬 main 통합 `ca73fd6`)를 실행한 기존 worker에서 새 관찰 구간을 측정했다. 2026-10-10 16:19 KST부터 10분 목표로 health를 약 2초 간격 조회했다. 마지막 표본 시각은 599.5초, 표본 299개이며 요청 실패는 0건이다. 같은 worker를 유지했고 정상 AU와 HTTP 메시지가 각각 9,327개 증가했다. 기기 상태 질의 성공은 47회 증가했고, 질의 오류·복구 실패·gap/reorder/corrupt·피드백 전송 오류·UDP 체크섬 오류는 모두 증가 0이다. 최대 AU 공백은 54.687초다. 측정은 카운터만 저장하며 추가 영상 구독자를 열지 않았다.

사용자에게 PC 다른 앱으로 약 30초 이동 후 복귀하고 계획/설정 탭을 2~3번 조작하도록 요청했다. 사용자는 **“계속 함께 바뀜”**이라고 확인했다. 243.5초 표본에는 정상 기기 응답(7.06초 전), 살아 있는 서비스, AU 공백 10.781초인데 `video_idle=false`였다. 해당 코드의 판정 조건상 이는 마지막 AU 이후 수락된 PC 입력이 있음을 뜻한다. 245.5초 표본에서 generation 3 → 4로 변경되고 AU 전송이 재개됐다. 이후 관찰 종료까지 generation 4를 유지했다. 사용자는 Chrome에서 조작했지만 재시작 버튼이나 새로고침은 누르지 않았다고 확인했다.

따라서 **재시작 0회 시험은 아니며**, 미반영 입력 뒤 영상 세션 복구 1회와 이후 정상 전송을 확인한 결과다. 입력이 실제로 화면 변경을 요구한 것인지, 화면 변화 없는 조작이었는지, 서버 watchdog와 브라우저 재시작 중 어느 호출이 직접 트리거였는지는 현재 카운터만으로 확정하지 못한다. 이 구간을 모든 영상 장애 해결이나 무중단 보장으로 표현하지 않는다. 10분 관찰과 30초 PC 앱 전환 확인은 추가로 완료했지만 실제 USB 단절 후 자동 복구는 별도 확인 대상이다. 전체 iOS 빌드·XCTest·원격 push·배포는 이번 추가 확인에서도 미실행이다.

## 추가 확인: 실제 USB 분리·재연결

10분 관찰 뒤 별도 구간에서 USB 연결 대수와 health 카운터를 약 1초 간격 관찰했다. 사용자에게 iPad USB를 약 10초 분리 후 재연결하고, 잠금 해제 상태를 유지하며 Chrome 새로고침/재시작 버튼을 누르지 않도록 요청했다.

관찰 시작 127.2초에 USB 대수 1 → 0, 기존 RTP 수신 task 종료를 확인했다. 133.2초 표본부터 health에 일시적 `URLError`가 나타났다. 139.3초 표본에서 USB 1대와 **다른 worker PID**, generation 1, 살아 있는 RTP 수신 및 AU 전송을 확인했다. 141.3초 표본에서 Chrome 구독자 1명과 HTTP 영상 메시지 증가를 확인했다. 최초 USB 0대 감지부터 새 구독자의 영상 전달까지 표본 시각 차이는 **약 14.1초**다. 이는 물리적 분리 순간이나 재연결 순간부터 정확히 잰 지연값이 아니다.

사용자는 **“자동으로 돌아옴”**, 이어 복구 후 계획/설정 탭 조작에 **“복구 후에도 양쪽 모두 바뀜”**이라고 확인했다. 서버 재실행·Chrome 수동 새로고침을 수행하지 않고 기존 supervisor와 브라우저 복구가 동작한 사례다. 새 worker에서 후속 관찰 중 generation 1을 유지했다. 본 시험은 영상·음성·HID 내용을 저장하지 않았으며 개인 기록을 변경하지 않았다.

이번 추가 확인으로 10분 관찰, 30초 PC 앱 전환/반복 조작, 짧은 실제 USB 단절의 worker 교체·브라우저 재구독·복구 후 입력을 확인했다. 장기 무중단 안정성, 오래 분리한 기기의 재연결, 잠긴 기기, 반복 단절/재시도 상한 소진은 검증하지 않았다. 정상 제어 응답만으로 인코더 정상 여부를 확정하지 못하는 한계도 유지한다. 추가 코드 변경 없이 결과 문서만 검토·공백 검사 후 커밋하고 공통 잠금으로 로컬 main에 통합한다. 전체 iOS 빌드·XCTest·원격 push·배포는 미실행이다.
