# Windows USB iPad 검증 — 2026-10-09

## 목표와 현재 판정

Mac/Xcode 없이 사용자의 실제 iPad에서 GymNote 화면을 관찰하고, 원격 터치로 사용자 시나리오를 검증한다. BrowserStack의 2분 체험 제한을 피하는 로컬 경로다.

- 사용자와 에이전트 모두 실제 GymNote 설정 화면을 확인했다. HTML 모사 화면이 아니다.
- 원격 터치 성공은 미확인이다. 실행·계획 탭 클릭 후에도 설정 화면이 유지됐다.
- 영상이 반복 정지·복구되어 아직 자동 사용자 실험에 사용할 수준으로 검증되지 않았다.
- 실제 기기는 iPadOS 27.2, 설치 앱은 0.1.85/build 85다. 클라우드 조사 대상 0.1.88과 버전이 다르므로 이 결과로 build 88의 시작 문제를 해결했다고 판단하지 않는다.

## 로컬 실행 환경

기존 Apple Mobile Device Service와 USB 연결을 사용했다. Python 3.14 환경의 의존성 빌드가 실패하여 저장소의 무시 경로 `.validation-tools/ipad-usb/python312/`에 공식 Python 3.12.10 embeddable과 pymobiledevice3 11.26.0을 설치했다. 전역 Python·PATH·Git 설정은 변경하지 않았다.

기기의 개발자 모드는 이미 켜져 있었다. `mounter auto-mount`로 개발자 디스크 이미지를 준비했으며, 화면 서버는 userspace 터널로 연결됐다.

```powershell
.\.validation-tools\ipad-usb\python312\python.exe -m pymobiledevice3 developer core-device display serve-web --bind 127.0.0.1 --http-port 8766 --no-audio
```

PC Chrome에서 `http://127.0.0.1:8766/`를 연다. 서버 종료는 실행 터미널의 Ctrl+C를 사용한다. `--no-motion-idr` 추가도 비교했으나 끊김은 재발했다. 현재 프로세스의 수명·PID는 세션에 종속되므로 재접속 시 다시 확인한다.

## 관찰한 문제

- 서버가 `no AU progress`를 기록하고 약 5~8초 정지 후 스트림을 재시작했다. 이는 영상 연결 증거이며 GymNote 앱 충돌 증거는 아니다.
- Windows 창 위치가 바뀌어 최초 클릭은 대상 창 불일치로 거부됐다. 창을 다시 관찰한 뒤 클릭을 재시도했다.
- 관찰한 실행 탭 좌표로 로컬 `/touch`의 단일 tap도 비교했다. 서버의 `ok` 응답은 큐 접수이며 UIKit 터치 성공을 증명하지 않는다.
- backboardd의 digitizer 거부 메시지만 잠깐 필터링했으나 출력은 없었다. 원인 배제 근거로 사용하지 않는다. 로그 조회 프로세스는 종료했다.
- Windows에서는 AAC-ELD 디코더가 실패했다. `--no-audio`는 뷰어의 자동 소리 재생을 끄는 옵션으로, 기기 오디오 스트림 생성 자체를 막는 옵션이라고 설명하지 않는다.

## 개인정보와 다음 검증

리스닝 주소를 `127.0.0.1:8766`으로 재확인했다. LAN 공개, 클립보드 동기화, 보안 설정 변경, 사진·연락처·메시지·전체 백업 수집은 수행하지 않았다. 화면 캡처에는 보이는 내용이 포함되므로 GymNote만 표시하고 테스트 데이터로 실험한다. 비밀번호가 없는 로컬 서버는 PC의 다른 프로세스에 노출될 수 있어 실험 종료 시 종료한다.

1. 사용자가 iPad에서 실행 탭을 직접 눌렀을 때 PC 영상도 바뀌는지 비교한다.
2. 영상은 정상이고 원격 터치만 실패하면 화면 회전 좌표·HID 세션 상태·기기 OS 호환성을 조사한다.
3. 영상 안정성 및 왕복 터치를 입증한 뒤 테스트 데이터 시나리오를 실행한다. 앱 재설치로 기존 사용자 데이터를 지우지 않는다.

앱 코드 변경·전체 iOS 빌드·XCTest·원격 push·배포는 수행하지 않았다. 설치 파일·원본 기기 로그·기기 고유 식별자는 Git에 포함하지 않는다.

## 후속 진단: 반복되는 Stream offline

사용자는 iPad에서 직접 탭을 누르면 PC 영상도 바뀐다고 확인했다. 이는 사용자 진술이며 에이전트가 직접 본 탭 왕복 결과와 구분한다. 직접 조작의 영상 반영과 원격 HID 터치 성공은 별개의 판정이다.

설치된 11.26.0 코드에서 뷰어는 새 프레임이 3초간 없으면 오프라인 문구를 표시하고, 서버는 정상 AU가 5초간 없으면 스트림을 재시작한다. 문구만 숨기거나 타임아웃만 늘리는 것을 영상 안정화로 처리하지 않는다.

### 내용 없는 카운터 측정

무시 경로의 임시 `diagnose_stream.py`는 패킷 증가량·마지막 정상 AU 경과 시간·구독자 수만 출력한다. `probe_stream.py`는 로컬 `/stream.bin`의 4바이트 길이 + 메시지 프레이밍을 읽고 영상 데이터를 즉시 버린다. 영상·음성·클립보드 내용은 진단 파일로 저장하지 않는다.

- `--no-motion-idr --rctl --max-bitrate 5000` 조건에서도 구독자가 없던 구간에 패킷 증가량이 0으로 떨어졌고 정상 AU 경과 시간이 9.2초, 14.2초 등으로 늘었다. 관찰 당시에는 브라우저가 새 서버에 재접속되지 않았다.
- 브라우저 대신 읽기 검사 클라이언트 하나를 연결한 45초 구간에 총 2,037프레임, 3,666,281바이트를 받았다. 같은 구간에 서버의 `no AU progress in 5.6s` 재시작이 한 번 기록됐다.
- 이 결과는 브라우저/WebCodecs를 사용하지 않아도 전달 중단이 재현됨을 보여준다. 기기 인코더, USB/userspace 터널, 수신·재조립 처리 중 어느 지점이 원인인지는 아직 미확정이다. 비트레이트 저하·키프레임 옵션·오디오 차단으로 해결됐다고 보고하지 않는다.
- 검색에서 발견한 [상류 이슈 #1759](https://github.com/doronz88/pymobiledevice3/issues/1759)는 작성자가 자신의 클라이언트 프레이밍 오류로 철회했다. 현재 환경의 알려진 결함이나 동일 원인의 증거로 사용하지 않는다.

### 진단 서버의 개인정보 차단

후속 관찰에서 뷰어가 `Sync: on`을 표시했다. 에이전트는 이를 켜지 않았으며 활성화 경위나 그동안의 복사 내용을 추정하지 않는다. 서버를 중지하고 사용자에게 off 전환을 안내했다. 이후 접근성 상태에서 `Sync: off`를 확인했다. 클립보드 내용은 조회하지 않았다.

현재 임시 진단 실행기는 설치 라이브러리 파일을 수정하지 않고 실행 프로세스에서 클립보드 HTTP 경로를 차단하며 기기의 오디오 스트림 생성도 건너뛴다. `/clipboard`, `/clipboard/events`, `/clipboard/image`, `/audio.bin` 모두 403을 확인했다. HTTP 핸들러 구조가 예상과 다르면 시작을 거부한다. 이는 로컬 진단용 제한이며 정식 제품 기능이나 감사 완료된 범용 서버로 배포하지 않는다.

```powershell
.\.validation-tools\ipad-usb\python312\python.exe .validation-tools/ipad-usb/diagnose_stream.py developer core-device display serve-web --bind 127.0.0.1 --http-port 8766 --no-audio --no-motion-idr --rctl --max-bitrate 5000
```

이 파일은 해당 PC의 무시 경로에만 있다. 기본 `serve-web` 명령으로 재실행하면 위 차단은 적용되지 않는다. 기본 명령을 개인정보 차단 서버로 설명하지 않는다.

### 남은 작업

1. GymNote를 다시 연 상태에서 뷰어를 새로고침하고 실제 브라우저 연결을 재검증한다. 홈 화면·개인 앱이 보이면 캡처·터치를 멈춘다.
2. 패킷 수신 중단과 AU 재조립 실패를 나눠 측정한다. OS·userspace 터널·전송 피드백의 호환성을 원인 후보로 유지한다.
3. 영상 안정화 전에는 원격 터치 및 가상 사용자 실험을 완료로 처리하지 않는다. 반복 불안정이 남으면 기존 AirServer 관찰 경로 또는 단발 화면 캡처 방식과 비교한다.

## 2026-10-10: 연결 복구와 PC 앱 전환 수정

검은 화면에서 어제의 서버가 살아 있었지만 `userspace dial plane is closed` 오류와 프레임 수신 중단을 확인했다. 개인정보 차단 서버를 새 USB 터널로 재시작하자 새 영상 프레임이 들어왔고 사용자가 화면 복구를 확인했다. 사이트 HTTP 응답만으로 실제 화면 수신을 보고하지 않는다.

사용자가 처음에는 탭 전환 때 끊긴다고 설명했으나, 이후 **아이패드 탭이 아닌 PC에서 다른 앱을 열었다가 뷰어로 돌아오는 상황**이라고 정정했다. 앞선 설명을 GymNote 탭 이동 결함의 근거로 사용하지 않는다. 전송 피드백을 끈 뒤 짧은 시험에서는 사용자에게 offline이 보이지 않았지만 같은 시기 서버에 AU 정지·재시작 기록은 남았다. 장기간 안정화로 판정하지 않는다. 에이전트가 만든 내부 브라우저 탭도 남아 있어 종료했다. 두 조치의 인과관계는 확정하지 않았다.

`scripts/ux_simulation_usb_viewer.py`와 `simulation/usb/`에 재현 가능한 로컬 어댑터와 검사를 추가했다. PC 백그라운드에서 프런트엔드의 자동 PLI·재시작을 보류하고, 복귀 시 유예·디코더 재생성·종료된 HTTP 스트림 재접속을 수행한다. 서버의 진짜 패킷 중단 watchdog은 유지한다. 기존 개인정보 차단도 정식 실행 경로에 포함했다. 설치 라이브러리 파일은 수정하지 않았다.

사용자가 PC 클릭·스크롤 전달은 되지만 좌표가 어긋난다고 확인했다. 실사용 회전 오류 보고를 조사해 [비교 절차와 출처](../../../simulation/usb/README.md)를 정리했다. 다른 도구의 보고를 해당 기기의 확정 원인으로 사용하지 않았으며 좌표 보정은 미적용이다.

검증: 백그라운드·복귀 유예·중복 이벤트·반복 복귀, 패치된 전체 JS 문법, 개인정보 GET/POST 경로 8개 차단, 오디오 생성 차단, 변경된 상류 소스 거부 검사 통과. PC 실제 앱 전환 후 복귀와 좌표 비교는 패치 적용 후 사용자 확인이 필요하다. 앱 코드 변경·전체 iOS 빌드·push·배포는 없음.

## 2026-10-10: 실기기 좌표 대응 확인과 보정

사용자는 왼쪽 스크롤이 위쪽으로 움직이고, 가로 화면 터치가 세로 기준으로 전달됨을 확인했다. 이어 PC 오른쪽 위가 iPad 왼쪽 위, PC 오른쪽 아래가 iPad 오른쪽 위라고 설명했다. 이를 근거로 영상 좌표 `(x,y)`→세로 HID 좌표 `(y,1-x)`를 적용했다. 앞 절의 좌표 미적용 상태는 이 변경 이전의 기록이다.

클릭·드래그·스와이프 버튼에 같은 변환을 사용한다. 기존 canvas CSS 환산과 영상 역회전은 유지한다. 기본 자동 모드는 원본 영상이 가로일 때 확인된 90° 보정을 사용하고 세로일 때는 그대로 전달한다. 반대 가로·뒤집힌 세로·무보정은 페이지 선택기로 전환한다. 양쪽 가로 방향 자동 감지는 구현하지 않았다.

검증: 모서리 4개·중심·드래그 축·CSS 배율/픽셀 비율·세로·반대 회전·영상 회전 중복 보정 방지·경계 제한 검사 통과. 전체 패치 JS 문법, 이전 백그라운드 회귀 검사와 개인정보 경로 8개 차단 검사도 통과했다. 수정 후 실제 탭 선택과 목록 드래그의 성공 여부는 사용자 확인이 남았다. 개인 화면 캡처나 실제 기기 입력을 자동 실행하지 않았다. 전체 iOS 빌드·push·배포는 없음.

### 후속 실기기 확인: 270°로 방향 정정

90° 선택 상태에서 사용자는 좌우 드래그가 반대로 전달되고 하단 탭보다 훨씬 아래를 클릭해야 선택된다고 보고했다. 270° 모드로 바꾼 뒤 **보이는 그대로 입력됨**을 확인했다. 앞선 모서리 설명만으로 90°를 확정한 판단을 정정하고 기본 가로 변환을 `(1-y,x)`로 변경했다. 추가 위치 오프셋은 적용하지 않았다. 현재 가로 방향의 클릭·드래그는 사용자 확인을 받았지만 반대 가로·세로 실기기 시험과 장시간 연결 안정성은 별도 확인 대상이다.

좌표 회귀 검사를 실제 확인된 기본 방향으로 갱신했고 반대 90° 선택 검사도 유지했다. 전체 JS 문법·좌표·백그라운드·개인정보 차단 검사 통과. 전체 iOS 빌드·push·배포는 없음.
