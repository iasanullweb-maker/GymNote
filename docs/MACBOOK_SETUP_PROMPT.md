# 맥북 GymNote 개발·배포 환경 설정 프롬프트

현재 상태(2026-10-09 후속 사용자 결정): **Mac 개발 환경 준비와 iPhone 설치·화면 확인은 보류**하고 iPad 마무리를 우선한다. 아래는 이전에 작성한 환경 이전용 프롬프트다. 새 작업자가 문서를 읽었다는 이유로 설치·push·배포를 시작하거나 여기의 과거 승인 범위를 적용하지 않는다. 사용자가 이전 작업을 다시 요청하면 최신 로컬·원격 상태와 승인 범위를 확인해 사용한다.

맥북의 Codex 또는 Claude에 아래 프롬프트 전체를 한 번 붙여 넣는다. 이 문서를 GitHub에서 읽는 경우 `codex/macbook-handoff` 브랜치의 최신 파일을 사용한다. 실제 설정과 검증은 맥북에서 실행해야 한다.

---

이 맥북을 GymNote의 개발·검증·배포 컴퓨터로 설정해줘. 계획만 설명하지 말고 도구 설치, 코드 이전, 로컬 빌드·테스트, 실행 확인, 반복해서 사용할 명령 준비까지 완료해줘. 현재 제공된 Computer Use로 필요한 앱과 브라우저를 조작하고, Git·설치·빌드·파일 편집은 가능한 한 터미널과 전용 도구를 사용해줘.

저장소는 https://github.com/iasanullweb-maker/gymnote.git 이다. Windows에서 최신 로컬 작업을 `codex/macbook-handoff` 브랜치로 보존했다. 이 브랜치와 최신 원격 main을 비교해서 양쪽 변경을 보존하고 시작해줘. 고정된 과거 커밋으로 되돌리지 마. 프로젝트 위치는 기존 맥북 체크아웃이 있으면 그것을 재사용하고, 없으면 `~/Developer/GymNote`로 해줘.

## 이 요청의 승인 범위

- 개발에 필요한 무료 도구 설치, 설정, 저장소 clone/fetch, 별도 작업 브랜치·워크트리 생성, 코드 수정·검증, 로컬 통합, GitHub 작업 브랜치 push와 검증된 변경의 main push, 기존 GitHub Actions를 통한 GymNote 릴리스·AltStore 소스 갱신을 승인한다. 이미 승인된 단계마다 재확인을 반복하지 마.
- 유료 가입·결제, 계정 삭제, 기존 앱 데이터 삭제, 강제 push/reset, 다른 작업의 변경을 버리는 처리는 승인하지 않는다. 기존 사용자 설정과 인증 정보도 보존해줘.
- 로그인, 2단계 인증, Apple 약관 동의, 관리자 암호, macOS가 요구하는 권한 승인은 사용자가 직접 해야 하는 경우에만 정확한 화면과 필요한 행동을 알려줘. 암호·토큰을 채팅이나 Git에 넣지 말고 공식 인증 화면과 Keychain 등을 사용해줘. OS 보안이나 에이전트 승인 정책을 우회하지 마.
- 사용자가 직접 처리해야 하는 단계가 생기면 독립적으로 가능한 작업을 계속하고, 해당 단계가 완료되면 원래 작업을 이어가줘. 완료되지 않은 인증을 완료된 것으로 가정하지 마.

## 1. 환경과 현재 작업 확인

1. macOS 버전, CPU 종류, 여유 디스크, 현재 프로젝트 폴더, Xcode·Command Line Tools·Homebrew·Git·GitHub CLI·XcodeGen·Node·Python 설치 여부를 확인해줘. 현재 맥북에서 실제 실행되는 도구를 사용해줘.
2. Computer Use의 macOS 네이티브 앱 제어가 실제 제공되는지 확인하고, 제공되는 도구의 지침·스킬을 먼저 읽어줘. Windows 전용 스킬을 맥에서 실행하지 마. 기능이 없거나 권한이 막혀 있으면 설치·Git·빌드 등 터미널로 가능한 작업을 진행하고 필요한 UI 단계만 구체적으로 알려줘. 터미널로 빌드한 것을 화면까지 검토했다고 보고하지 마.
3. 기존 체크아웃이 있으면 브랜치·미커밋 변경·워크트리를 확인해줘. 다른 채팅이나 Windows에서 진행 중인 작업과 겹치는 통합·배포가 있는지도 가능한 범위에서 확인하고, 진행 중인 배포를 중복 실행하지 마.
4. 저장소의 `AGENTS.md`, `HANDOFF.md`, `README.md`, `project.yml`, `docs/LOGIN_SETUP.md`, `.github/workflows/build.yml`, `.github/workflows/check.yml`을 읽어 실제 최신 구조를 따라줘. 이 프롬프트가 이후 추가된 사용자 지시를 덮어쓰지 않도록 해줘.

## 2. 무료 개발 도구 설치와 인증

1. Xcode는 이 macOS에서 사용 가능한 안정 버전을 공식 경로로 설치하거나 기존 설치를 재사용해줘. 전체 Xcode가 필요한 작업을 Command Line Tools만 설치하고 완료 처리하지 마. 첫 실행 구성요소, 활성 developer directory, iOS/iPadOS 시뮬레이터 runtime까지 준비해줘. `xcodebuild -version`, `xcrun simctl list devices available`로 확인해줘.
2. Homebrew는 공식 설치 방법과 CPU에 맞는 경로를 사용해줘. 이미 있으면 재설치하거나 shell 설정을 중복 추가하지 마. GitHub CLI, XcodeGen, 프로젝트 검사에 필요한 Node·Python 등을 설치해줘. 전체 CI에 필요한 DB 검사 도구는 워크플로를 확인하고 로컬 실행 필요성을 판단해줘.
3. GitHub CLI는 브라우저 인증을 사용하고 저장소 읽기·쓰기 및 Actions 조회 권한을 확인해줘. Git 작성자 이름과 이메일은 기존 설정이나 인증된 사용자 정보를 확인해서 사용하고 임의로 만들어 넣지 마.
4. Codex/Claude 앱을 사용 중이면 맥북의 실제 저장소 폴더를 프로젝트로 연결해줘. 사용 가능한 UI 또는 앱 전용 도구로 처리해줘. 다른 에이전트 앱이 설치되지 않았으면 그것 때문에 Xcode 설정을 중단하지 마. 컴퓨터 제어의 화면 기록·손쉬운 사용 등 필요한 권한만 안내하고 광범위한 보안 해제는 하지 마.

## 3. Windows 작업 이전

1. 기존 폴더가 없으면 저장소를 clone하고 `origin/main`과 `origin/codex/macbook-handoff`를 fetch해줘. 이전 브랜치가 없으면 오래된 main만 가져와 최신이라고 보고하지 말고 Windows 쪽 이전 브랜치 게시가 필요하다고 알려줘.
2. 이전 브랜치에는 화면 가독성 개선, 일상 반복·알림, 실제 세트 횟수 기록 등 Windows 로컬 변경이 담겨 있을 수 있다. 커밋 이력과 실제 파일을 확인해 포함 여부를 판단해줘. 원격 main이 더 최신이면 그 변경도 보존해줘.
3. 설정 작업은 `codex/macbook-setup` 또는 이름이 겹치지 않는 `codex/` 브랜치와 별도 워크트리에서 해줘. 검증 후 시작 당시 기존 작업 브랜치에 로컬 통합해줘. 통합 직전에 기존 폴더의 브랜치와 미커밋 변경을 다시 확인해줘.
4. Windows의 워크트리 디렉터리나 `.git` 경로를 그대로 복사하지 말고 맥북에서 새 체크아웃·워크트리를 만들어줘. 기존 Windows 폴더는 이전과 검증이 확인될 때까지 보존해줘.
5. `AGENTS.md`, 인계 문서, 개발 스크립트는 Git으로 이전하고, Xcode 프로젝트·Config·빌드 결과는 재생성해줘. 앱 사용자 데이터와 기기 Keychain은 Git으로 이동되지 않으므로 기존 iPad 데이터는 유지해줘.

## 4. Xcode 프로젝트와 로컬 설정

1. 이 프로젝트는 `project.yml`을 사용하는 XcodeGen 프로젝트다. `xcodegen generate`를 실행하고 `GymNote.xcodeproj`를 Xcode에서 열어줘. 프로젝트 파일만 직접 바꾸고 다음 생성 때 설정이 사라지는 방식은 피하고, 공유 설정은 생성 원본에 반영해줘.
2. 먼저 iPad 시뮬레이터로 앱·위젯을 빌드·실행해줘. 서명은 현재 CI의 시뮬레이터 설정을 참고해 필요한 설정을 명시해줘. 실제 장치 서명이 없어도 시뮬레이터 개발·테스트는 진행해줘.
3. `GYMNOTE_SUPABASE_URL`, `GYMNOTE_SUPABASE_PUBLISHABLE_KEY`는 GitHub Actions Variables와 설정 문서에서 확인하고 맥북의 로컬 빌드에 적용해줘. 관리자/service-role 키를 앱에 넣지 마. 로컬 설정은 Git에서 제외하고 프로젝트 재생성 후에도 재사용할 수 있도록 해줘. 공개 설정이 준비되지 않으면 게스트 실행을 검증하고 로그인 미검증을 별도로 보고해줘.
4. 실제 iPad가 연결되고 적절한 Apple 개발 팀을 사용할 수 있으면 앱과 위젯의 서명·App Group을 함께 맞춰 설치·실행해줘. bundle ID나 App Group을 바꿔야 한다면 기존 앱과 공유 데이터·로그인·위젯에 미치는 영향을 먼저 확인해줘. 유료 개발자 계정이 없다는 이유로 구매를 진행하지 말고 기존 AltStore 배포 경로를 유지해줘.
5. 권한이 허용된 Computer Use로 Xcode Preview와 Simulator를 직접 확인해줘. 기존 계획 캘린더·분야 전환 Preview를 사용하고, 운동 실행 화면 확인에 Preview가 필요하면 별도 샘플 데이터로 추가해줘. 테스트용 샘플이 실제 계정 저장소를 덮어쓰지 않게 해줘.

## 5. 검증과 바로 쓸 수 있는 명령

1. 현재 CI에 있는 Swift 모델·계정·일상·알림 등의 검사를 확인하고 적절한 로컬 검사와 iPad 시뮬레이터 XCTest를 실행해줘. 로그인·저장·계정 데이터 변경 검사는 바로 실행해줘. DB 정책·계정 삭제 검사는 기존 CI로도 확인해줘.
2. 앱과 위젯의 Release 빌드를 수행해줘. 수정해야 할 오류가 있으면 의미를 확인해서 고치고 필요한 검사만 다시 실행해줘.
3. 실제 UI에서 운동명·횟수, 큰 세트 원·완료 버튼, 완료·되돌리기, 실제 횟수 입력과 수정, 계획 스크롤, 일지·기록, 일상 반복·알림 설정을 확인해줘. 네이티브 화면 캡처를 남기고 시뮬레이터 테스트와 실기기 테스트를 구분해줘. 실제 알림 도착·OAuth 로그인·Live Activity 등 확인할 수 없는 항목은 미검증으로 명시해줘.
4. 저장소의 기존 도구를 재사용하면서 `setup`, `run`, `test`, `build`, `release-check` 같은 반복 가능한 명령을 Makefile 또는 macOS 스크립트로 준비해줘. 설치된 도구는 재사용하고, 실행할 때마다 프로젝트 생성·필요한 로컬 설정 주입이 안정적으로 되도록 해줘. 시뮬레이터 이름이나 CPU 경로를 임의로 하드코딩하지 마.
5. 배포 명령은 검토·검증·브랜치 확인 후에만 push하도록 설계해줘. 단순 환경 설정 명령이 실수로 main을 push하지 않게 해줘. `.xcodeproj`, DerivedData, IPA, 로컬 인증 설정을 Git에 추가하지 마.
6. 코드를 검토하고 변경 목적·실행 방법·검증 결과·미검증 항목을 `HANDOFF.md`와 macOS 설정 문서에 기록해줘. 문서만 바꾼 것을 앱 코드 검증 완료로 혼동하지 마.

## 6. 통합과 기존 방식의 배포

1. 처음에는 작업 브랜치를 push해서 현재 `Validate GymNote`와 `Build IPA` 워크플로를 실행하고, 대상 커밋에 대한 전체 필수 검사·앱/위젯 Release 빌드가 모두 성공했는지 확인해줘. 실패하면 원인을 고치고 그 커밋을 재검증해줘.
2. 최신 원격 main을 다시 fetch하고 진행 중인 다른 작업을 보존하며 통합해줘. 검증 이후 기능 코드가 바뀌면 통합된 최종 커밋을 다시 검증해줘. 원격이 앞섰다고 force push하지 마.
3. 검증된 최종 커밋을 기존 작업 브랜치에 로컬 통합하고, 이미 동일한 코드가 배포됐는지 확인한 뒤 필요한 경우 main에 push해 기존 GitHub Actions 배포를 한 번만 실행해줘. 기존 IPA·릴리스·AltStore 배포 구조를 유지해줘. Mac 환경을 만들었다는 이유로 CI나 배포 서비스를 새로 갈아엎지 마.
4. main의 Build IPA 성공, 대상 커밋, `build-N`/`latest` 릴리스와 IPA, AltStore `source.json`의 버전·다운로드 URL을 확인해줘. 실제 다운로드 링크가 맞는지 확인하고 워크플로 시작만으로 배포 완료라고 하지 마. 기존 릴리스를 임의로 직접 삭제하지 말고 저장소의 기존 자동화가 관리하게 해줘.
5. 완료 응답에는 맥북 프로젝트의 절대 경로, 바로 실행할 명령, 로컬 통합과 원격 push 여부, 전체 빌드·검사 결과, 실제 배포 버전·링크, 남은 사용자 인증 또는 실기기 확인 항목을 간결하게 알려줘.

이 프롬프트의 목표는 다음 요청부터 이 맥북에서 바로 코딩하고 화면 확인·테스트·검증된 배포까지 진행할 수 있는 상태를 실제로 만드는 것이다. Windows에서 진행 중인 작업과 배포를 중복 실행하거나 덮어쓰지 말고, 추가 판단이 필요하지 않은 단계는 자율적으로 완료해줘.
